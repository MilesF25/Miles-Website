Sonification, the translation of data into non-speech audio. That is basically what I did: turned bytes into sound. I decided to do this in Rust because this is a low-level project, so a low-level language would be fitting. There are three main parts to this project: getting the file from the user, extracting the bytes, and turning the bytes into sound.

The simple parts are getting the file and extracting the bytes. In the get_file() function, I used the clap crate to handle the input file from the user and then a simple match to handle extracting the bytes from the file. In the read_file_to_bytes() function, I read the file and get the size of the file in bytes, then I iterate through each byte and add it to a list. There probably is a more efficient way of doing this, but this is simple and easy to understand. I did have an issue here due to how Rust handles ownership. Originally, I had something like (let size = file.metadata()?.len();), but I couldn't do this because file was being used by the reader. So anything after it couldn't access it. The great thing about Rust is that there seems to be a function for every situation. It took some time, but I learned about get_ref(). It let me borrow the file variable even though it was being used.

            fn read_file_to_bytes(file: File) -> io::Result<(u64, Vec<u8>)> {
                let mut byte_int_list = Vec::new();
                let reader = BufReader::new(file);

                // gets the ref of the file from reader

                let size = reader.get_ref().metadata()?.len();

                //iterates through reader and puts bytes
                for byte in reader.bytes() {
                byte_int_list.push(byte?);
                }

                Ok((size, byte_int_list))
                }

The final function is turning bytes to sound. It was tricky and hard to understand because I do not have a background in audio, so I had to use AI to help me with that part. Basically, the goal is to turn the byte into a sound. A byte can range from 0-255, so we need a way to turn that into a sound. To do that, we use an equation: f = B + (v x m). F being the frequency in hertz, B is the base frequency offset, v is the byte value, and m is the multiplier. Here is what it would look like with values: f = 200 + (byte x 10). The reason B, the base frequency offset, is set to 200 is because we need to have a good starting sound. If it was zero, then there would just be silence. 200Hz is equivalent to the hum of a refrigerator, a low, deep hum so any speaker will be able to play it. The multiplier, m, is set to 10 so we can spread everything out. The range will be 200Hz-2750Hz. That way, the human ear can clearly distinguish between each sound. If we didn't have this, everything would sound similar.

Once I had the frequencies, I had to figure out how to actually generate the audio waves. I found a great Reddit post that explained the physics of sine waves. You can find it here: sound_and_sine_waves_the_physics_of_audio

After reading it, I decided sine waves are the best option, but now how do I actually code it? This is where AI is very handy. I gave it some context about what I was doing and where I was currently stuck, and it came up with this. The AI explained that computers can't just draw a smooth, continuous wave; instead, they have to take thousands of tiny snapshots every second, which are called "samples." To make a sound that actually sounds like a clear note, you usually need 44,100 of these samples for every single second of audio. It gave me a formula to calculate the position of the wave for each of those snapshots: sin(2 * PI * freq * time). By plugging my byte-to-frequency math into that formula, I could finally turn those raw numbers into a digital wave that a speaker understands.

But then, it pointed out a huge problem I hadn't thought of, scale. If I played every single byte in a 1MB file for just a tiny fraction of a second, the resulting audio would be nearly three hours long. To fix this, I made a "stride" calculation. Basically, the code looks at the total size of the file and calculates how many bytes it needs to skip so that every file, no matter how big it is, results in a nice,about 60-second or less "audio fingerprint." There could be a better way to implement this, I realize that even if two files are similar size, skipping over the chunks will make them sound very different. I also learned about a "windowing" feature, which is like a quick volume fade-in and fade-out for every byte. This stops the speakers from making a loud popping sound when the frequency jumps.
